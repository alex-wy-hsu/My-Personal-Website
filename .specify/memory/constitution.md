# 我的個人網站 憲章

## 核心原則

### I. 程式碼品質（不可妥協）
所有正式生產程式碼必須遵循既定風格指南，並在審查前通過自動化 linter/formatter。拉取請求（PR）應當小而專注，並包含明確的說明與變更理由。程式碼必須模組化、具備文件說明，並暴露清晰的介面。可維護性為首要考量：最小化全域狀態，優先使用明確契約，並為重要模組提供 README 級的使用說明。

### II. 測試標準（測試優先）
測試為必要條件：包含單元測試、整合測試，於適當情況下加入端到端測試。新功能必須先撰寫會失敗的測試（Red → Green → Refactor）。CI 必須執行測試並阻止未通過測試的合併。對於關鍵模組，建議測試覆蓋率目標為至少 80%；覆蓋率僅為信號而非唯一門檻，重點在於有意義的斷言與防止迴歸。

### III. 使用者體驗一致性
網站必須採用單一設計系統與元件庫，以確保視覺與互動的一致性。對外頁面須達到 WCAG AA 無障礙標準。主要的 UX 模式需有文件說明，重大流程變更需接受設計審查並附上回歸檢核表。

### IV. 效能要求
為頁面載入、可互動時間（TTI）與 API p95 延遲等項目建立效能預算。新增功能需包含效能論證，必要時附上基準測試或剖析資料。發現效能回退需在合併前修復；CI 可加入針對關鍵頁面的輕量效能煙霧測試。

### V. 可觀察性與簡潔性
互動功能應具備基本的可觀察性：結構化日誌、度量指標與錯誤回報。實作應以簡潔、易測試為優先，避免過度複雜的巧妙寫法。文件中應說明預期失敗模式與復原步驟。預設採取簡單方案，僅在必要時再引入複雜性。

## 額外限制
技術選擇應優先靜態優先、尊重隱私，並盡量減少不必要的相依。生產資產應最佳化（圖片、字型等）。任何第三方服務需評估其隱私影響與可用性要求。

## 開發工作流程
- 分支命名：功能分支 `feat/<簡短描述>`；修補分支 `fix/<簡短描述>`。
- 拉取請求：至少一名審查者批准（對外或高風險變更建議兩名），CI 必須通過，並在 PR 描述中明確列出 UX 變更與測試覆蓋情況。
- CI/CD：合併至 `main` 分支前必須通過 linters、測試與建構檢查。合併後自動部署至生產；回滾流程須簡單可執行。
- 版本與發行：公開套件遵循語義版本；網站內容可在有意義時使用內部遞增標記。

## 治理
憲章的修訂須以 Pull Request 形式對本檔案提出。修訂需包含明確的理由、遷移步驟（如適用）及影響評估。變更需由專案維護者批准（至少一名維護者 + 提案者）後才能合併。若為破壞性治理變更（刪除或重定義原則），須提高 MAJOR 版本並撰寫遷移指引。

合規檢視：關鍵原則（程式碼品質、測試、UX 與效能）建議至少每年或在重大平台變更時進行檢視。檢視中發現的不合規項目必須被列為優先修復事項。
